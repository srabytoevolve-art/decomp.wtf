# Master System (Z80)

Master System and Game Gear games were written in Z80 assembly. A function matches when your source assembles,
at the function's address, to exactly the game's bytes, *and* reads as source: code is instructions (not `.db`),
and every address the project has a name for is written as that name. The listing you're given already
assembles; your work is to make it the game's source: names, labels, comments, constants.

Syntax (decomp.wtf's assembler; WLA-DX / sjasmplus style)
- `name:` labels; `.loop:` local labels (scoped to the last plain label); `NAME = value` equates.
- Numbers: `$1F`, `0x1F`, `1Fh`, `%1010`, `'A'`; expressions with `+ - * / & | ^ << >> ~`, `$` = here.
- `ld a,(ix+5)`, `ld (iy-2),a`, `jp (hl)`, `ex af,af'`, `out ($BE),a`, `in a,(c)`, `rst $38`.
- Undocumented instructions are spelled `sll`, `ld ixh,a`, `in f,(c)`, `out (c),0`. An instruction with a
  second encoding the game happens to use is written with its opcode: `neg.ed4c`, `ld.ed6b hl,($C000)`.
- `.db 1, 2, "TEXT"`, `.dw label` only for data the function keeps among its code (a table after `jp (hl)`,
  text after a call). `.org`, `.incbin`, `.include`, `.bank` and macros aren't allowed: the judge places code.
- The context (get_context) is assembled before your function: equates and comments only.

Addresses, banks and the mapper
- The Z80 sees 64 KiB: ROM at $0000-$BFFF in three 16 KiB slots, RAM at $C000-$DFFF (mirrored to $FFFF).
- Bank 0 is always in slot 0 ($0000). Code maps other banks into slot 1 ($4000) or slot 2 ($8000) by writing
  the bank number to `$FFFE` / `$FFFF` (names: MAPPER_SLOT1, MAPPER_SLOT2). The mapper ignores bank bits the ROM
  doesn't need: `ld a,$82 / ld (MAPPER_SLOT2),a` maps bank 2 of a 512 KiB game.
- So a function's address is its bank and where it runs: `func_00158A3C` is bank $15 at $8A3C. split_function
  takes these 8-digit addresses (`0x00158A3C`).
- A call into another slot reaches whatever bank is mapped there at the time. The brief names the bank decomp.wtf
  worked out; when the code picks the bank from a RAM variable (a "module" number), several functions in
  different banks share an address: use the name the brief gives.

Reading the code
- `rst $08`..`rst $38` are one-byte calls to the routines at $0008..$0038; games put their busiest helpers there
  (set VDP address, read a table word, jump through a table). `rst $38` / $38 is the frame interrupt (IM 1).
- Jump tables: `ld hl,table / rst $20`-style dispatchers, or a call followed by `.dw` entries (the dispatcher
  pops its return address to read them). Name the table and its entries.
- Ports: VDP_DATA $BE, VDP_CONTROL $BF (also status), VDP_VCOUNTER $7E, PSG $7F, JOYPAD_1 $DC, JOYPAD_2 $DD.
  A joypad bit reads 0 while its button is held.
- Ghidra's C reading (in the brief) helps see the logic; it isn't what's compiled.

Naming (see guide("naming") too)
- Functions after what they do (`UpdatePlayer`, `LoadStagePalette`), RAM after what it holds (`wPlayerX`,
  `wFrameCounter`), tables `...Table`/`...Ptrs`. rename_symbol changes the name everywhere, matched code too.

C projects (homebrew, SDCC)
- Games built with devkitSMS are C: the project's compiler is SDCC, and your C is compiled with it, then
  assembled and judged like assembly. SDCC passes the first argument in A or HL and the second in L/E or DE
  (`sdcccall(1)`, SDCC 4.2+): match the argument types to how the target reads them. Locals live at -n(ix);
  `static` functions and data follow the function in its area.
